# Financial PDF synchronization

SQLite on Writer remains authoritative. Database backup, normal PDF delivery and client-platform billing publication are separate flows. A successful database backup never acknowledges a PDF upload.

Migration 19 is additive and transactional, preceded by a verified SQLite snapshot. `document_sync_queue` contains only normal invoice/Credit Note IDs, generation, state, attempts, retry deadline, safe error and verification time. It contains no protected-register payloads or secrets. Existing noncancelled invoices with no Drive reference and credits with pending/error cloud status are queued, not reissued. Already confirmed historical documents are not bulk rewritten.

Invoice creation/revision/status and Credit Note creation/status update the queue inside the financial transaction. Writer PDF regeneration also enqueues the invoice, including open/print/share preparation. Viewer may save a local copy but cannot enqueue, retry or upload. Deleted/cancelled invoice jobs are removed by triggers, without deleting remote financial history.

The worker runs on startup and every 30 seconds, processing up to ten eligible documents serially per batch. Manual and automatic uploads share document locks; folder discovery/creation is serialized. Disconnection preserves work. Transient failures use exponential delay plus jitter, capped at roughly 15 minutes; eight failed attempts or permanent errors require explicit retry. No network calls are made from the status endpoint. Drive file requests in invoice upload and folder discovery use 30-second timeouts; a timed-out write is reconciled by identity before retry rather than assumed to have failed remotely.

Confirmation is conditional on the same database, Writer role and queue generation, after remote content checksum/size verification. A concurrent edit cannot be acknowledged by an older upload. Legacy credits are moved and updated in place, not deleted/recreated. Normal invoices now use the single-file contract below. No layout or financial formula changes are intended.

The global nonmodal banner shows pending/blocked counts and ten representative references/errors, with an accessible icon-only retry action on Writer. Viewer displays the state in its latest database replica, not a live assertion of remote state. Protected-register synchronization remains session-gated and is deliberately outside this queue.

Tests cover persistence/restart, rollback, role and database changes during IO, cancellation, stale completion, duplicate folders/files, response loss, deterministic PDFs, retry caps, redacted error categories, keyboard retry, Viewer denial and uninterrupted input focus. Local tests use synthetic data and provider doubles; they do not establish recovery on the real Writer/Drive account.

Local verification on 2026-09-08: 261 automated tests passed; TypeScript and renderer/main/preload production build passed; targeted lint passed (repository-wide lint retains existing warnings). Browser regression suite passed both Credit Note entry paths, normal/protected numeric editing, company search, the new document banner, keyboard retry, Viewer denial and focus retention. A separate visual browser check confirmed the banner renders without an error overlay. Windows installed-app and real Drive delivery have not been verified for this change.

Release requirements: Windows installed upgrade through migrations 19–20, one real pending invoice and credit, verify existing Drive IDs/bytes, reconnect/restart, and check the banner clears only after verification. Preserve the pre-migration backup; prefer a forward fix if needed. Do not delete/reissue invoices or replace current business data to recover a PDF transfer. No production data or Drive files are modified by local development/tests, and publication requires separate user authority.

## Single invoice PDF contract (migration 20)

The user explicitly requested one mutable PDF shared by Drive and client-platform publication, named `Invoice_<invoice_number>.pdf`. This replaces the earlier immutable technical-file strategy. The Hub protocol payload still uses `drive_file_id`, not the filename. Drive content can become current before platform totals refresh: this cross-provider window is eventual consistency, not an atomic PDF/metadata commit. Live platform download/caching behavior is not verified by local tests.

The additive `invoice_drive_identity` table preserves the transport ID and company/store binding separately from the current published-PDF field. Migration copies known IDs without network calls or financial edits. Future invoice invalidation still clears `invoices.drive_file_id` until remote verification. A changed ownership binding fails closed; the code never silently repurposes another company's known file. Protected-register PDFs remain out of scope.

On a requested save/regeneration, discovery accepts exact short/historical names or the strict legacy `Invoice_<Writer UUID>_<invoice ID>_<revision>_<hash>.pdf` pattern inside the configured invoice tree. Existing known ID wins; otherwise an identified legacy technical file or the unique readable PDF is adopted. A readable duplicate must match the bytes of an identified technical copy or the newly generated official document. Ambiguity, inaccessible roots, mismatched content, missing known IDs and concurrent changes block without creating replacements. The chosen file is renamed and moved with [Drive v3 files.update](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/update), retaining its ID. Identical bytes/name/parent skip the remote write. A financial no-op preserves line IDs and document revision.

Duplicate metadata and the chosen identity are durably remembered before rename/update, so response loss is resumable. Duplicates remain untouched until the company's latest publication is acknowledged, with no pending upload or staged delivery. The worker then verifies the active PDF's checksum/name/size/parent and each captured duplicate's unchanged metadata/scope before moving that duplicate to Drive Trash (never permanent delete). Old duplicate links cease serving after cleanup; the active canonical link remains. Trash recovery is manual. Cleanup retries have backoff/jitter and stop after eight failures, with a safe banner error and explicit retry. Processing is bounded to ten invoices per worker batch and one hundred candidate copies per invoice.

Tests use synthetic Drive responses and SQLite fixtures: new/legacy/technical naming, one ID across edits and retries, no-op saves for imported/manual invoices, deferred cleanup, lost update/trash responses, changed active/duplicate bytes, other Writer/invoice names, role changes, cached publication, pending uploads, cleanup retry caps, migration rollback and financial integrity. Deployment and actual Writer/Drive/client download acceptance remain separate. Do not downgrade an operational Writer to the former two-file implementation; prefer a forward fix and retain its migration backup. Local file/WhatsApp naming is unchanged by this Drive-specific correction.

Single-file local verification on 2026-09-08: all 272 automated tests pass; TypeScript, targeted lint, renderer/main/preload production build and whitespace checks pass. Existing build size/module warnings remain. No UI/template layout or native printing/sharing changes were made, so the earlier browser evidence remains applicable to those unchanged surfaces. No installer, release feed, live Drive file or platform record was changed.
